# Keel Core 5.0.1 用户使用指导

本文档面向在应用中集成 **keel-core** 的开发者，说明版本前提、依赖方式、模块边界与主要能力的使用要点。更细的设计讨论可参考仓库内
`docs/项目设计与实现分析.md`；集群后台服务（Maids）的补充说明见 `src/main/java/io/github/sinri/keel/core/maids/README.md`。

**按子模块细分的使用说明** 已拆分为多份分册，与 `module-info.java` 中 exports 包一一对应；完整列表见 *
*[文档目录](index.md)**。

---

## 1. 版本与适用范围

- **库名称**：Keel-Core（Maven 工件名一般为 `keel-core`）。
- **本文档版本线**：**5.0.1**（与 `gradle.properties` 中 `version` 所标识的发行线一致；开发中可能为 `5.0.1-SNAPSHOT`）。
- **运行环境**：**Java 17**（Gradle 中 `languageVersion` / `release` 均为 17）。
- **模块化**：本库发布为 **JPMS 模块**，模块名为 `io.github.sinri.keel.core`。

本库建立在 **Keel 框架分层**之上：对外能力大量依赖 **keel-base**（如 `Keel`、`KeelVerticleBase`、配置抽象等），并与 *
*keel-logger**、**Vert.x** 等协同工作。单独引入 `keel-core` 时，传递依赖会带入上述栈，请注意与项目其余依赖的版本对齐。

## 2. 引入依赖

### 2.1 Maven

```xml

<dependency>
    <groupId>io.github.sinri</groupId>
    <artifactId>keel-core</artifactId>
    <version>5.0.1</version>
</dependency>
```

### 2.2 Gradle (Kotlin DSL)

```kotlin
dependencies {
    implementation("io.github.sinri:keel-core:5.0.1")
}
```

实际坐标与可用版本以 **Maven Central** 或团队制品库为准。本仓库 `gradle.properties` 中的 `keelBaseVersion`、
`vertxVersion` 等可与主项目对齐，减少传递依赖冲突。

### 2.3 JPMS（`module-info.java`）

若应用本身使用模块路径，需在模块描述符中声明对本模块的依赖，例如：

```java
module com.example.app {
    requires io.github.sinri.keel.core;
    // 若直接使用 keel-base 公开 API，可能还需要：
    // requires io.github.sinri.keel.base;
}
```

`io.github.sinri.keel.core` 对 **keel-base**、**Vert.x 核心与 mail**、**CommonMark** 等使用了
`requires transitive`，下游模块在未直接引用这些 API 时，通常仍能在编译期解析到传递模块（具体以 JDK 与构建工具行为为准）。

## 4. 核心使用思路

### 4.1 Verticle 与 `Keel`

多数「服务形态」组件（`Sundial`、`QueueDispatcher`、`Intravenous`、`Funnel`、`IntravenouslyCutter`、Maids 下各类）继承 *
*keel-base** 的 `KeelVerticleBase`，通过 **部署 Verticle** 接入 Vert.x 事件循环与生命周期。

业务代码侧通常需要：

1. 持有或获取 **`Keel`**（keel-base 提供的异步门面，封装 Vert.x 操作）。
2. 在合适的时机 **`deployMe(...)`** 部署上述 Verticle（具体选项见各类 JavaDoc，如 `ThreadingModel`、`DeploymentOptions`）。

集群相关 Maids 的约束与协作方式，务必阅读 **`maids/README.md`**（序列化限制、SharedData 锁、节点实现一致性等）。

### 4.2 缓存

- 入口类型：`KeelCacheInterface`。
- 常用工厂：`createDefaultInstance()` 获得默认可过期实现；`getDummyInstance()` 获得不缓存的占位实现（便于测试或关闭缓存）。
- 同步外观另见 `KeelSyncCacheAlike` / `KeelAsyncCacheAlike` 层次，按场景选择。

典型用法：配置默认 TTL、`save`、`read`、以及「不存在则计算并写入」类方法（见接口 JavaDoc）。

### 4.3 单节点调度与队列

- **`Sundial`**：单节点定时；内部按分钟对齐并结合 Cron 计划触发任务，匹配时会部署子 Verticle 执行计划（见类上说明）。
- **`QueueDispatcher`**：**仅单节点**；抽象类需实现取任务、信号与工作状态等（见 `QueueTask`、`QueueSignalReader` 等配套类型）。

使用前请确认部署拓扑：不要把单节点语义组件误用于多副本无协调场景。

### 4.4 `Intravenous` 与 `IntravenouslyCutter`

- **`Intravenous`**：FIFO 处理注入的「滴液」对象；`instant(...)` / `instantBatch(...)` 创建单条或批量处理实现。
- **`IntravenouslyCutter<T>`**：从 **Vert.x `Buffer` 流** 累积并 **`cut()`** 出 `T` 列表，再交给 `Intravenous`；流结束需调用
  `stopHere()` / `stopHere(Throwable)`，并用 `waitForAllHandled()` 等待处理完成（详见类首 JavaDoc 步骤说明）。

### 4.5 `Funnel`

按 FIFO 执行异步任务（`Supplier<Future<Void>>`），带可配置休眠与中断唤醒逻辑，适合需要「排队串行化」的异步管线。

### 4.6 Markdown

- **`KeelMarkdownKit`**：默认启用 GFM Tables 扩展；可传入扩展列表与对 `Parser.Builder` / `HtmlRenderer.Builder` 的回调以定制行为。
- 常用方法：`convertMarkdownToHtml(String)`、`convertMarkdownToHtml(Reader)`；亦可取出底层 `Parser` / `HtmlRenderer` 自行扩展。

### 4.7 邮件（SMTP）

- **`KeelSmtpKit`**：自 **5.0.0** 起标记为 **`@Deprecated`**。推荐改为使用 **`SmtpConfigElement#toMailConfig()`
  ** 得到 Vert.x **`MailConfig`** 后，直接使用 **`MailClient.create` / `createShared`**（见 `KeelSmtpKit` 类注释）。
- **`SmtpConfigElement`**：从 keel-base 的 **`ConfigElement`** 树构造，读取 `hostname`、`port`、`username`、`password`、
  `ssl` 等字段。

### 4.8 阻塞 IO 与 Vert.x 流桥接

- **`AsyncOutputReadStream`**：将 **`InputStream`** 适配为 Vert.x **`ReadStream<Buffer>`**。工厂：
  `AsyncOutputReadStream.create(Keel)` → `wrap(InputStream)` → 按 `ReadStream` 语义使用；读完可通过 **`readOver()`** / *
  *`getReadOverPromise()`** 获得传递字节数约定（见类型 JavaDoc）。
- **`AsyncInputWriteStream`**：将 **`OutputStream`** 适配为 **`WriteStream<Buffer>`**，工厂与 `wrap` 对称，写完关注 *
  *`writeOver()`**。
- **`IOUtils`**（标记为 **`@TechnicalPreview`**）：
    - `toReadStream(Keel, InputStream, Handler<ReadStream<Buffer>>)`：先 `pause`，在 handler 中完成 `pipe` 等装配后再
      `wrap` 与 `resume`。
    - `toWriteStream(Keel, OutputStream, Handler<WriteStream<Buffer>>)`：在 handler 装配后 `wrap`。

**使用注意**：阻塞读在 worker 上执行；**超时、关闭与 `InputStream` 线程安全**等边界条件会随具体实现与源类型变化。对
`System.in`、长阻塞或需可中断的场景，应在业务层明确资源生命周期，并阅读实现类 JavaDoc 与测试用例所表达的语义；不宜假设「超时即等同于底层 read 已取消」。

### 4.9 其他工具包

- **`utils`**：如 `JsonUtils`、`StringUtils`、`FileUtils`、`TimeUtils`、`DigestUtils`、`NetUtils`、`ReflectionUtils`、
  `RuntimeUtils` 等，按类名语义直接使用（细节以 JavaDoc 为准）。
- **`utils.cron`**：`KeelCronExpression` 等与 `Sundial` 计划配合。
- **`utils.runtime`**：运行时与 JVM 状态快照（如配合监控、诊断）。
- **`utils.value`**：`ValueBox` 等轻量值容器模式。
- **加密与 TOTP**：按包路径选择具体类；注意算法、填充与密钥管理须符合安全规范。

## 5. 日志与空安全

- 日志 API 来自 **keel-logger**（模块中 `requires transitive io.github.sinri.keel.logger.api`）。组件内常见
  `LoggerFactory`、`SpecificLogger` 等用法，与 Keel 生态一致。
- 源码使用 **JSpecify**（`@NullMarked` 等）标注空安全意图；业务侧若启用相关静态分析，可与这些注解对齐。

## 7. 小结

**Keel Core 5.0.1** 在 **Java 17 + JPMS** 下提供：与 **keel-base / Vert.x** 一致的 **Verticle 式服务组件**（单节点 *
*Servant** 与集群 **Maids**）、**进程内缓存**、**Markdown**、**SMTP 配置与 Vert.x 邮件客户端衔接**、以及丰富的 **utils**（含 *
*Cron**、**运行时**、**加密**、**阻塞 IO 与异步流桥接** 等）。

集成时请：**选对单节点/集群语义**、**通过 `module-info` 仅依赖 export 包**、**邮件优先走 `SmtpConfigElement` + `MailClient`
**、**实验性 IO 工具注意阻塞与生命周期**。更多行为细节以对应类的 **JavaDoc** 与测试为准。
